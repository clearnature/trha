 工作室版本 2.11.0
 c774ff9
本版把工作室的外壳从墙换成电子：窗口、资源、发布线、三平台自行更新与全部操作系统能力都重新落到内核与传输层上，两个外壳跑同前置。有三条生命主线：计划周期成为授权第一个的一个形态，ask成为回合交互；沙盒把外网与先授权拆除两轴，解决文件对bash也拒绝；外围维护改由经济边界触发，长工作站内可反复，recall可搜索已分区。 2.10.0 起 131 个工作。

路径升级：Windows安装器改为按用户安装，并在安装时接管旧的Wails全机安装（会弹卸载一次确认，拒绝也不影响本次安装）；Linux的.deb与旧包同名，dpkg按升级处理；macOS替换自身捆绑包。

新增
Studio 改由 Electron 承载
Wails 的资源服务器把hub.Handler()挂成进程内中间件——没有端口、没有 CORS、没有第二条传输，独立进程的控制渲染器够不到。现在 hub 跑在环回 HTTP 上，NewLoopbackGate是上面必须的边界：策略来自打开监听存在的同时配置，请求必须发往本监听、必须以本监听为原点才能打开、必须以本次启动铸造出的结构。无原点的读放行（支持导航不发原点），无原点的写拒绝。四类拒绝各有独立错误码。凭证只走cookie（查询token会落进请求行、历史与referrer），由直接设置，页面JS读取不到。
Electron 外壳：内核由外壳派生，stdout 传一行版本化 JSON 握手（版本不认识就拒绝启动，日志一律走 stderr），stdin 是租约（父进程第一关闭即内核排空，覆盖崩溃与退出，三平台无信号参与）。页面七个/_studio/，一条规则即完成路由——反过来「内核枚举所有路由、剩下落到页面」是资源服务器逼出来的形状，内核每加一个就要改一次。渲染器沙盒化、上下文隔离、无node，preload 只递出动词。
四个窗口控件相互直接对接window.go.main.App，绕过港口层；入口点探测靠Wails运行时不再决定chrome长什么样。两者都改问HostPort，它同时回答是否自绘标题栏。CSS按该属性纽扣外壳名分支，并同时发--wails-draggable与-webkit-app-region信号——它们是互不理睬的两套机制。
窗口的四项OS能力接回，内核侧零队列（不加端点、不加事件种类）：拖入文件重新以路径到达（渲染器只拿得到File，而要对文件本身的回合不能在数十副本上做，预加载经webUtils解析）；保存文本与导出插件包走外部自己的对话框（压缩包仍来自浏览器构建已在用的端点）；通知复用internal/notify与共享的[notifications]设置。
状态栏图标成为协议绑定。货架设置经Wails绑定读写配置文件，折叠数来自同进程饲养的追踪器，第二个外壳只能带一份副本。现在三条路由分别是「人设的偏好」「图标画的折叠」「写入两者的唯一入口」：偏好是持久默认，写入后直接回答它变成什么样了；折叠是投影，每次读都重算，丢一帧下次读就补回来，所以是拉取通知事件。文案在有数字和词条表的地方按桌面语言一起，画图标的外壳不再各存一个预设逻辑。
目录选择器成为HostPort动词，透明答案互不折叠：路径、""（面板被取消）、null（该外壳没有选择器）——把两者当成一件事的调用方把面板打开两次。面板从哪个目录打开由内核/workspaces回答，外壳不自存副本；可新建目录，否则「只能打开存在目录」读起来就是「这个应用无法开新项目」。
一个数据主目录只允许一个Studio，无论哪个外壳持有窗口。相同主目录两个窗口就是它每个会话文件的两个写者，而两个写者就是把成绩单分叉成一长恢复副本的原因；彼此这条规则写在Wails外壳里，另一个外壳没有。身份移到internal/instanceid——一直就是「规范化后的数据主目录」而不是「一个应用」，安装版、便携版与canary因此能互相找到，经软链到达的主目录归位到它指向的那个。电子的锁键在profile目录上，于是profile放到该身份下，由平台回答「已在运行」。
远程主机能力从Wails外壳搬到internal/remotehost，两个动作由同一个经纪人构建同一个实现。拨号、在遥控器装内核、持有时序、给失败命名都不是废的事，而持有它们的就是前面的那个外壳——电子设备根本打不开远程区。remotehost被接通为下一步消防消防救援的端口、只由第三方装载，内核/控制器/工具层不得触达，三个例子住了这一点。
被阻塞的远程拨号，其提问成为规范状态。首见主机键或加了口令的私钥将拨号停止等人回答，反过来这个提问活在Wails上、经绑定返回。现在按三重身份确定地址（epoch是内核生命期、操作是哪次拨号、问id是哪个问题），重复回答同一件事幂等成功，后面回答取消是独立状态不存在。不建集线器等级事件流：唯一订阅者是一个人几秒内就回答完的模式框。
版本面板经GET /studio/versions与POST /studio/pin回答，内核里的update.Hub读目录，外壳只说明自己的安装。这内核确实算不出来的部分——电子束里os.Executable()指的是一个二进制引脚应用，版本烙在派生的进程上。目录地址是常量而不是安装说明，否则一个出口就能把它指向另一条产品线，那里的一端会把Studio更新成另一条产品。
安装某个版本成为两个shell交互说的动词：POST /update/install起编排（在internal/appupdate），GET /update/install是它的进度投影。进度是拉取不是流：一次成功的安装最后做的事就是结束那个本该在推流的进程。路由202返回而不是等待——接管发生后已没有可用于后续回答的东西。
macOS自更新补上第三个业主。它本是三方不是两方：旧应用授权交接、助手执行替换、新应用程序说明自己健康并了事务；替换方可以执行替换，但不能声明替换是健康的。这个业主随老外壳一起丢了，于是第一次成功的自更新就pending-update.json与回滚捆绑在一起留在原地，而ensureNoPendingUpdate把这个堆存储读成记账合法事务——之后每次更新都被「存在已待处理更新」拒绝。UpdateHealthWitness在启动时读一次待处理事务，自身不带路径与版本，所以调用方可能只确认其实际启动自的那个记账。
资源与发布线
make studio走 Electron。它取代的路径按构造就只能在 macOS 上跑了——裸 Go 二进制对 LaunchServices 不是 GUI 应用，脚本得先打成捆绑包重新启动；Electron 的开发本身就是.app，一个脚本服务所有平台。
Electron-builder 架构安装器、便携压缩包、磁盘映像与.deb，沿用 Wails 线的标识与产物命名——清单更新与发布工作流读的就是这些名字，这里改名等于发布一个没人会被通用的版本。架构在备份边界翻译：electron-builder 说x64，发布说amd64（更新器在跑 Go）二进制里，问的runtime.GOARCH）；映射不到的架构直接构建失败，因为静默的结果是一个描述“没有任何运行中的二进制会去问”的平台的结果。
三平台都在各自的 GitHub 上机上备份，并按发布线实际读取的叫契约校验真实产品：没有产品x64、有一个叫发布架构；清单通道旁没有电子更新元数据；内核与 SPA 是资源不是归档成员；studio-manifest把产品挂到运行程序所在平台的按键下。此时只有存在 Windows 的包真实过，macOS 与 Linux 靠的是一个配置文件加一次交叉编译。
发布线出电子包。Windows 与 macOS 都分两步备份，理由说一次：两步之间必须对包做点什么——那里是 Authenticode 签名，这里是公证与钉封；Linux 不需要，所以一步。Windows 签名契约点名两个文件除外一个：本壳既窗口发也发它派生的内核，只签外容器层他们在安装后仍以未签名状态在上面，而外面那层安装器已经被信任了。
.deb的包名、更新helper的路径/权限/属主与polkit策略由CI读真实包校验。helper的路径不是选择：polkit动作的exec.path标注式的就是它，授权只授给那一个；它同时也是Wails包占用的路径，所以一个目标同时满足策略与升级。--deb-user root显着声明——fpm对-s dir记录构建机的属性，而polkit不会执行一个调用者本可读取的helper，CI runner的uid最多那个文件等于安装得上、更新时拒绝。
桌面模块的Go测试首先进CI，三平台。 阿联酋Studio工作流只构建外壳，主工作流的套件完全是主模块的——其次更新引擎、它的提权助手、发布侧工具与两个外壳，只在维护者恰好本地跑过的地方是绿色的，而那会替换别人磁盘上运行中应用的代码。
计划生命周期成为一种状态
计划同时是一个原子 bool，承载两个问题：用户是否在这个工作流里，以及现在什么可以跑。bool 说不批准AwaitingApproval，也说不出「放弃是以后的工作、不是已经在途中的工作」——转换转换它就会在模型规划期间流式示意图的每调用一次重新性地放行。planmode.Runtime持有唯一的State{Phase, Epoch}，Active是派生索仓库；每次被接受的都抬高epoch（Submit与Revise也违约，因为它们都改变了当前非哪份授权）。供应商每个问卷都在采样前盖上其不稳定的状态，源epoch已当前的调用被暂时拒绝并被告知原因。
规划期间的副作用改在效果轴上判定。计划向模型承诺会拒绝写入、有副作用的shell、能力安装、记忆修改与可写委派，而委派没有被拒绝：边界测的是mutates，而task、、自身不记录任何变更——写发生在子代理里。在auto或yolo曼哈顿档下他们照跑，子代理还握着完整工具集。是叶子包，零值读作「有副作用」，所以一个失败打开委派按是否具备撰写能力拆分、、与有争议的子代理继续运行——那是一个计划做调研的方式。run_skilluse_capabilityplanmoderead_only_taskparallel_tasks
「规划期间这个能不能跑」双方有两个回答者（阶段门，以及一条测变更记账的循环策略），各自都不算错，洞在相互之间，而委派的修复只落到了其中taskpolicy一个planPhaseEffect。阶段性判定移到第一个效果之前并非仅在权限之前——代理只有在解析之后才说出最后的真实目标，而ResolvedCall.Commit按其自身契约位于接下来的检查之后，首先它跑在检查之前，所以一次被拒绝的规划调用仍然可能留下一条已提交的账本项。
假设拥有的决定成为投影。想要一个「等你处理」清单的前置，之前只能从事件里自己拼并记住看过什么——而那是把前面刚开始的重复重新揉回去的做法：一个面板、一对允许/拒绝，计划批准开始长得像权限提示。Decisions每次被问时从各自的业主派生，自身无状态，Kind指明方向、业主就是回答者（plan_approval回到ResolvePlanDecision，ask回到AnswerQuestion），刻意没有Decision.Approve。身份是业主就发出的id原样送回，过渡期因此天然无害。
工作室渲染拥有的计划周期。前期它把计划卡的结果折成审批布尔，再自行设置计划模式——本征损（修订与退出是不同的转换），生命周期变成一个状态之后生命还会跟内核自己的动作抢：前面的SetPlanMode(false)可能退出一个批准刚刚带进执行的工作流程。现在两端都把整个结果经ResolvePlanDecision送出。现在服务增加POST /plan-decision，然后不再持有该时回409与带码的拒绝——这是ARM客户端错误。窗口持有的、已已停止顺序的被封存而不删除：它不再可回答，但作为「发生过什么」的记录留在屏幕上。
待办的写入被区分成「改计划」与推进小时「执行」。接下来只持有一个事实——任务清单变了——于是每一轮同样重写两步的循环，与真正完成它们的循环产生同一个信号；这次工作背后的会话花了十二、1065次任务清单读取，完成步数固定在22.ClassifyTodoTransition从清单填写本身一次写入做了什么，身份取稳定的step_id（没有时取规范化文本），界面取位置。重新规划刻意推进不是：把它算作推进就等于允许一个信用卡的回合靠重写自己的清单来自我续命。
complete_step的结论来自任务清单。它开头每次签收都以「继续已推进任务列表，请继续下一步」结尾，而这句话是不知道是否还有下一步的情况下断言的；首先推进在完成并答案知道，只是模型唯一会读的那部分——工具结果——没带上它（#8816就是那个圆圈完成：最后一个待办，仍索要下一步，模型于是结果发明了一个，回合结束不了）。
把持有它的步骤id投影到模型读取得到的位置。complete_step把step_id为PreferRED，而相应标自投影计划起就为每一个持有一个——模型却从没被展示过：todoState不进提示词，todo_write只回统计，三个清单渲染器全打裸序号。于是模型能引用的只有被展示的序号，而那是重新规划在上面插入之后会插入的引用。
ask成为循环屏障
ask取得只有是用户能提供的东西。它不是请求权限的方式、不是计划卡、也不能替代代理自己能做的调研——而反过来那条准入判据（「无法从请求、代码或合理默认值中解决」）让模型把任何有看法的事都自行解决了。有推荐意见不等于这个选择归你：当两个合理选项会改变架构、公开API、数据模型、依赖、UX、通用、范围或任何不可逆的东西时，就问，并把推荐放在上面。
更要命的是相互。写在问题旁边的一切都存在于答案之前写的：ask("删除还是归档?")与write_file(...已删除...)在同一个里，无论用户怎么回答都会执行猜测。工具声明自己的屏障（而不按那个名字），扫描在调度运行之前；有争议的同批呼吁同样停止——共享同一个模块段才是问题，写不写不。被推迟的调用会被告知他们没有被带过来，以及为什么。
没有人可问的运行不再自己回答自己。旧的回退让模型「用你的最佳判断」，这与唯一撤回这里的规则直接矛盾——决定保持未解决，模型被指向conclude_blocked而不是一个它还得为辩护的猜测。任何阑尾都不代用户作答。
沙盒：外网与未知授权撤销两轴
network在安全带上实测：(deny network*)连Unix套接字一起拦截，于是关掉外网的用户同时失去了ssh-agent——ssh-add -l与SSH签名提交都停了，而这两件事都不需要互联网。反方向上，默认的network = true把假设的代理套接字发生了每一条命令，发现验证了它的值多少：在对话框上的私钥已被删除的前提下，最终shell仍然让后面的代理有了一个有效的签名。拒绝读取（ForbidReadRoots）这没有什么作用——持有股票与可以使用它是两回事。
Spec现在在Network境外指示HostAuthorities，策略点名服务节点路径，每个路由器按各自客户端的方式解析ssh_agent/ docker/ podman。默认只捕获ssh_agent：签名是编码工作流的日常，而容器守护进程的套接字是全机执行权。零值Spec什么都不授，新的调用点在明说都是预设的——MCP服务器因此不再获得任何授权。受治理的是三个点名端口，DBus、Wayland、X11、gpg-agent、keyring与任何套接字目前仍然有效，所以连接始终是「这些端点受治理」，立场是「交易所 IPC 被隔离」。
凭据文件对 bash 也读取拒绝。read_file拒绝~/.ssh/id_ed25519，而cat照样返回：凭据拒绝表只接收了进程内的读取工具，从来没有接收sandbox.Spec.ForbidReadRoots，于是 OS 边界放行了每一条 shell 命令——包括cp、tar与各个解释器，这也是无法在命令分类器里打的补丁原因。出网默认开启、自动档两半都放行，那所以次读取和后面的 POST 都不需要任何提示。internal/secrets现在持有两个消费者共读的那一小表：只安装机密字节的文件默认拒绝（SSH）私钥、~/.aws/credentials、~/.netrc、~/.git-credentials、~/.pypirc、gcloud ADC）。把配置混进秘密的文件刻意不在其中，而且是实测不推定：拒绝~/.config/gh/hosts.yml会让每次gh调用在启动时失败，拒绝~/.npmrc会静默改掉 npm 的全局前缀。[secrets] protect_credential_files = false可关闭。
上下文维护
压缩协议只认一条边界：声明窗口的compact_ratio。一个声明1,000,000代币窗口的供应商预设因此把触发点850,000，而一次真实会话跑了2,150轮、提示词达到了321,265——布局的37.8%，一次都没有维护被尝试过。宽敞与经济性是远端不同的边界：模型支持1M上面，不等于300K的提示词为几个代理循环反复重放是划算的。自动触发改为先到者：窗口的compact_ratio，或可视输入的context_soft_limit_tokens（默认160000，负值关闭）。
一个循环内可反复折叠其已关闭的回合。 一会儿循环只能被检查点一次，之后折叠区止于该循环的第一条消息，长到能二次旋转的循环的循环就得承载它过的第一轮——推动工作的那次循环在一个循环内持有321K令牌、2150轮，而折叠区只够到它的之前30K。现在检查点能够到的是该循环已关闭的事务：停止于closedPrefixEnd（该循环的每次调用都已完成的最后一点一次），所以在循环事务永远不会被分解，开启该循环的那条请求由keepIndexes逐字保留。
recall可以检索，只是定址。首先它只能读取其他东西已经命名过的位置，而命名者会衰减：折叠索引限制被窗口的1%、会裁掉最旧的行；canonicalOriginFor对任何位于先前投影内部的东西返回-1而不是二次，折叠的根本没有可推导规范的位置。底下什么都丢了——压缩的模型看到规范的东西，从不触碰碰碰规范的记录。所以recall增加了查询，在canonical[:CoveredCount]（后备存储，非绝投影）上走与历史相同的BM25语。搜索与读取占用原预算，空结果不均衡也不等于错误。搜索成本线性且足够小结果不需要索引：1k条已折叠消息2.3ms，5k条11ms，20k条44ms。
折叠索引器与摘要分工：buildFoldIndex基于摘要会记下它们的承诺而跳过「路径有且命令失败」的原因。逆转路径打破了这个承诺——mustFree下repairFoldCoverage量完成覆盖率就返回（正确，硬顶不是再叫一次摘要器的位置），以及摘要器彻底失败degradeFoldSummary了一个什么都不带的机械摘要。这两种情况下都同时缺席于摘要和索引，却仍保持规范记录里：数据留着，地址丢了。现在用同一个控制器回执自己写回路径与命令签名，只写摘要漏掉的部分。
子代理
争议子代理按写者的方式汇报。写者子代理以complete_subtask结束，接下来会拿它的每一条引用与自己观察到的行为对账；涉子代理首先以散文结束，回执仍进入父账本，但语义那一半以一个无法验证事件到达，两者之间没有任何连接工具附加的顺序是要点：readOnlySubRegistry先任何构建工具、论证子代理确实能调查点什么，然后才附上报告方式——先附加上的话，一个没有调研工具的子代理会因为握着提交发现的工具并通过能力检查，然后就做不到的工作报告。
报告完成和裁决，双方是一个词兼两义。complete_subtask对双重结果都回首「接受」：后续能背书的报告，与后续欠款报告过其顺利的报告，得到同词，差别在一个尾随的话里。 延迟显示子代理会得到怎么处理：份报告被退回则继续干活，10/10；首份欠款中止，4/4，两边无都异常。契约中「确切」一旦，作为你的最后一次工具调用”被移除——它在写下之前就已被证明伪：一个用“再行动”来响应被破坏的正义，不可能同时被一个只调用一次的子代理回避。
统计「子代理是否按被要求的方式收尾」的通道接收到了空处：全树没有任何类型实现SubagentHandoffSink，它也从未在capabilityContracts里注册过，因此RecordSubagentHandoff内部的类型断言在第一个包装器上就匹配不到，审计被丢弃——生产者有结构体、有接口、有绿色单测，这似乎是没人发觉的原因：一致性说明方法存在，只有调用栈能说明值到达了。另一处：每个子代理都发往subagentProgressTracker.wrap()，而它返回event.FuncSink，函数类型不实现任何可选能力，所以那个沉丢掉了全部十二条通道。在benchmarks/fanout-width上实测防守：subagent_handoff0→4，1 contract_shadow→ completion_report5，1 protocol_recovery→5，0→6，4 outcome_progress→39。

响应边界在循环提交之前被分类。被输出顶部截断的响应，彼此以「bash 的参数无效；它需要 "command"」到达模型——一个原因（finish_reason是长度），但只知道把它发给一次真正的会话获取收获的教训是不要再批量发独立调用，而这与整棵树的要求正相反，成本是每次调用一个循环。中断只可能切掉最后一次调用，所以只有它、且只在其参数解析失败时被丢弃。参数报错现在把解析器停止的字节引出并在下面加脱字符标志。
后台任务完成会唤醒拥有它的会话。执行层本就是异步的，代理的控制流不是：后台任务跑、排入一句话，然后要等用户开口模型才学得到它已经完成（#7948））。这里没有另外建运行时——会话收件箱本身就是一个。jobs发布CompletionEvent（一个身份不用说），控制器把它翻译成接着续写。哪条投递路径生效则靠读「是否有循环在跑」来决定：循环可能刚好在读与入队之间结束，转向尝试本身会报告身处世界。
task_token_budget补齐三条轴中缺的那条。TaskBudget自轮次计数下线后就带有三条轴，令牌那条是唯一一条启动从未映射的，任何键能设置它：却轴存在、被执行、打不开。它计模型做的工作量——usage.PromptTokens含CacheHitTokens，煽里160,000提示词有159,900来自硬盘，仍然总计160,000；推动当前工作的那次进程以99.9%命中率把 393.7M 输入 token 中的 393M 已占用服务器，若按缓存未命中计分，任何上限都会使永远跑下去。默认关闭。
Reasonix主目录像工作区根一样可被报表。办法每一层都从环境变量里回读它，然后绑定一个主目录的唯一是改进进程状态——这也是为什么第二个主目录意味着第二个进程，以及为什么internal/boot里没有东西能装东西。config.Roots是这个绑定，boot.Options.Home是入口。

最后安装：探测说能用、启动必崩溃
一个内核能否被驱动，首先只靠在serve --help里找到一个port-file来判断。但启动传的不止这一个——驱动那组晚了整条发布线才出现。于是一个只有前半组标志的旧内核通过探测了，带着--provider-broker被启动，在一个从未定义过的标志上退出。到达用户在20秒​​后的「发球」从未报告端口」：一个超时、一台机器、一个“查看日志”——而份日志已被失败删除清理掉。真因（那台机器上的内核来自另一条线）没有出现在任何一个地方。

现在探测问的就是启动会传的那一组，并有测试断言彼此一致。形状还有两处：失败清理与各自抄了一次「一次服务的记录由哪些文件组成」，而是经纪人加进来时双方都漏了，于是每次失败的启动都把本机的遗言保持远程；remote test与remote connect接不同的参数，于是就把前面一条connect会走的路报关闭、把一组被拒绝的路报开成着。

失败也补上缺的那个身份：ErrNoReleaseForBuild说「这个构建没有可安装的发布」，排在各条路自己的错误码——被指装curl的人装完了仍然路。npm那条路装完后版本还不够时，现在报是没有版本还不够，而不是「安装到PATH」之外。没有摘掉npm这条路：它需要硬编码之前「npm上是1.x」这会超过的判断。

另外，一个由程序启动、来自broker的内核不再在启动时查询余额——它按设计没有自己的辅助，那次查询必然失败，于是每份启动日志的都常驻一条与故障无关的错误，而那份日志只在排查故障时才会被打开。

其它
MCP：会话的 MCP 生命期不再继续构建它的那次请求；连接一个待确定服务器是决定一个并被记录等待；仓库报表的服务器会回答；读取 Claude Code 实际写入的范围。
能力：目录是索引是每一条描述；批处理分发器在模型读取得到的地方被命名；工具自己的名称解析到它自己。
代理：从来没有修改运行的调用不再判定失败一次；在参数中途被中断的调用即使终端看起来完整也被丢弃；子代理的工具id只做一次命名空间；依赖中断不再丢掉委派。
被拒绝的完成会说明哪一条不成立、缺乏什么。
判断哪些文件是测试不再靠读工作区。
界面要过而目录里没有的八个 i18n 键。
最新的指令可以取代它之前的副本。
长文件名不再覆盖它自己的+N -N；数据存储说明文字不再成为那一行的崩溃压缩区。
内部
控制器按周期拆成协作者：会话的生命周期与持久化、菱形编排及其守卫、MCP服务器编排、把输入变成一个循环与运行一个循环、取消与善后，各自组成生命文件；一次循环投影的从八处改为前置一处。
项目本身的规则、记忆索引、技能目录与版本控制状态移出每个项目共享的缓存分区，由轮询承担。
安装脚本现在会被真正执行而不仅仅是被写出来：下载、校验摘要、解包、定位、读回版本，全程真跑一次shell。
macOS 按架构分别构建而不是结构单一的通用包；产物按其中的包命名；不再文件夹包里没有任何东西会读取的文件。
macOS已使用开发者 ID 签名并公证，打开时不需要清除隔离属性。Windows的窗口、内核与安装器都经过 SignPath 进行了 Authenticode 签名。Linux从.deb安装。

三个平台全部自动更新：Linux走自己的包，Windows运行下一个安装器，macOS替换自身包。
